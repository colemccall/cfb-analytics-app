# CFB Analytics App

Vanilla HTML/JS/CSS frontend for the CFB Analytics Platform. Served via GitHub Pages — no build step, no framework, no npm.

**Live demo:** [colemccall.github.io/cfb-analytics-app](https://colemccall.github.io/cfb-analytics-app)

---

## What This Is

A college football analytics platform that answers a core question: **which players are genuinely elite vs. which are hyped?**

The app surfaces EDGE ratings — opponent-adjusted per-game production scores — for FBS players from 2008–2025. A 3-star receiver who dominates against Power 4 defenses will rate higher than a 5-star recruit who hasn't produced. The gap between recruiting hype and real production is what this platform is built to find.

## Pages

| Page | URL | What it does |
|------|-----|-------------|
| Home | `index.html` | Editorial front door — computed storylines (risers, breakouts, hidden gems), the opening slate, research headlines. Every number is computed from `data/` at load time |
| Players | `players.html` | Draft board — filter by season, position, conference, min OVR; click any row for the full modal (stats, EDGE percentile, rating breakdown, comps) |
| Teams | `teams.html` | Team ratings with sub-scores (pass offense, run defense, etc.); ranked roster (no depth chart: there is no depth data); schedule |
| '26 Season | `season2026.html` | The 2026 schedule: 25 games to circle ranked by matchup quality, per-team slates, and a plain statement of what is live vs. still coming |
| Ratings | `ratings.html` | Talent-vs-production scatter (green = 8+ OVR above trend) plus top-50 leaderboards per position group |
| Research | `research.html` | Three live analyses — team performance residual, recruiting-class ROI, Engine D breakout calls — each a sortable, filterable table |
| Methods | `methods.html` | How every number is computed — formula as the code runs it, evidence, limits, alternatives considered (`METHODS` registry) |
| Build Log | `changes.html` | What each working pass changed, tried, measured and left unfixed (`CHANGES` registry) |
| How It Works | `info.html` | The user guide: what each page answers, every panel and control, and a glossary of every mark on a number, drawn by the real render helpers (`GUIDE` registry). Restates no formula — links to Methods |

## The menu

`menu.html` is the app: a home page (the top ten, best players, week results, playoff picture, movers, recruiting classes, transfers, every row a link), a page for every team (`#/team/52`, with its roster, depth chart, schedule, recruiting, transfers and history), rankings, standings, players, the playoff bracket, recruiting, the transfer portal and the reference screens, one screen at a time. A player card has Overview, Stats and Career sections. Mouse first, with keyboard and Gamepad API support. It has its own files (`css/menu.css`, `js/menu*.js`, token block `.menu-app`) and reads the same data through `dataLoader.js`; standings, the portal and the depth order share `js/leagueData.js` with the site. A destination is written as `data-to="#/team/52"` and the router opens it, so any element can link. Following a team is optional (a button on its page). The layout follows the early-2010s console franchise menus from memory; art and copy are original. 2026 roster rows and cards show three ratings (last season, projection, earned to date), never merged. See the Guide ("The menu: home, teams and players") and Methods (`three-ratings`).

## Tech Stack

- **HTML5** — semantic elements, no framework
- **CSS** — custom design system, two themes (dark + light) listed in `CONFIG.THEMES` and driven entirely by CSS custom properties; `tools/theme-check.mjs` enforces the skin contract and contrast floors enforced by `tools/contrast-check.mjs`
- **JavaScript** — vanilla ES6+, no bundler
- **Fonts** — Barlow Condensed (display) + Inter (body) via Google Fonts
- **Data** — static JSON files in `data/`, generated by the pipeline. No backend, no API keys, no runtime dependencies.
- **Hosting** — GitHub Pages. `main` is the source of truth; the legacy `clean-arch`
  branch is kept fast-forwarded to the same commit until the Pages source is confirmed
  as `main` in repo settings.

## Script Load Order

Every page loads scripts in this order:

Two blocks. At the very top of `<body>`, so the theme applies and the chrome exists
before first paint:

```text
1. js/config.js  — CONFIG, theme-keyed palettes, ratingColor()/ratingTextColor(),
                   seasonList(), fillSeasonSelect(), entity links
2. js/shell.js   — applies the theme, injects the sidebar + mobile tab bar
```

Then at the end of `.main-content`:

```text
3. js/dataLoader.js — the single fetch layer (_load cache, fetchAllPlayers,
                      fetchTeams, fetchSeasonGames, …)
4. js/ui.js         — render primitives (ovrPill, posBadge, deltaChip, onThemeChange, …)
5. js/dataTable.js  — createDataTable() / createFilterBar()  [pages with tables]
6. page module      — home.js | playerSearch.js | teamsPage.js | ratingsDisplay.js
                      | season2026.js | findings.js + findingPage.js
                      | methods.js + methodsPage.js | changes.js + changesPage.js
                      | guide.js + guidePage.js (info.html; also loads methods.js
                        and changes.js for link titles and the latest version)
```

`config.js` must load first — everything else depends on `CONFIG`. No page carries its
own nav markup or theme script; `shell.js` owns both, keyed off `<body data-page="…">`.

## Data Flow

```text
Pipeline (cfb-analytics-pipeline)
  └── scripts/12_export_frontend_json.py
        └── data/
              ├── players_{season}.json          — players with OVR, stars, team, position
              ├── rosters_{season}.json          — team rosters
              ├── schedules_{season}.json        — games and results (2026 = schedule only)
              ├── transfers_{season}.json        — portal moves (2021+ only)
              ├── similar_players_{season}.json  — top 5 comps per player-season
              ├── team_stats_{season}.json       — per-game team metrics
              ├── ratings_by_position_{season}.json — top 50 per position group
              ├── teams.json / team_ratings.json — team OVR + sub-scores, all seasons
              ├── team_history.json              — year-by-year team progression
              ├── player_transfers.json          — player-centric transfer history
              ├── team_performance.json          — SP+ vs recruiting-talent residual (script 13)
              ├── recruiting_roi.json            — class hit rates (script 14)
              ├── trajectory.json                — projections + model accuracy (script 15)
              ├── trajectory_detail.json         — per-player explanation, drivers, comparables
              ├── manifest.json                  — seasons, last_played_season, projected_seasons
              └── research/index.json            — published research findings

Frontend (this repo)
  └── fetches from data/ at load time — that's the whole data layer
```

**`data/players_{season}.json` and `data/team_ratings.json` must be generated by running pipeline script 12 before the app shows any player or team data.** Pages load but show empty states until then.

## Configuration

`js/config.js` needs no credentials — the app reads only static files. The values that matter:

```js
const CONFIG = {
  DATA_BASE:          "./data/",
  FIRST_SEASON:       2008,   // oldest exported season
  LAST_PLAYED_SEASON: 2025,   // newest season with EARNED ratings
  CURRENT_SEASON:     2026,   // season the app defaults to (projected)
  PROJECTED_SEASONS:  [2026], // seasons whose ratings are model output
  // ...
};
```

Three season constants, because "the current season" means two different things. Anything
retrospective — hidden gems, research, "best class we've graded" — must read
`LAST_PLAYED_SEASON`, or it will narrate model output as fact. `isProjectedSeason(season)`
is the single test; `ovrPill()` calls it internally, so passing a `season` is enough to get
the PROJ treatment and a caller cannot forget to.

These mirror `data/manifest.json`, which the pipeline writes. config.js loads synchronously
before any fetch so it cannot read the manifest at runtime — instead a pipeline contract test
(`tests/test_export_contract.py::test_frontend_season_constants_agree`) fails if they drift.
After exporting a new season, update both.

## Theme System

Two first-class themes, set as `data-theme` on `<html>` by `js/shell.js` before
first paint:

| Value | Token block |
|-------|-------------|
| `dark` | `:root` |
| `light` | `[data-theme="light"]` overrides |

Resolution order: `?theme=dark\|light` URL override (used for deterministic
screenshots) → the saved `localStorage["cfb-theme"]` choice (legacy
`dynasty-dark` / `mid` values migrate to `dark`) → the OS `prefers-color-scheme`.
The sidebar swatches persist the choice and dispatch a `cfb:themechange` event.

**Any JS that computes a color must repaint on that event** — rating pills,
position badges and chart marks are theme-derived, so page scripts register
`onThemeChange(render)` (`js/ui.js`) to re-render from the in-memory cache.

**Contrast is enforced by a tool, not by eye.** After changing any token or
palette value, run:

```bash
node tools/contrast-check.mjs
```

It asserts text ≥7:1, muted ≥4.5:1, borders ≥1.8:1 (≥3:1 for `--border-strong`),
and every rating/position fill ≥3:1 against its luminance-guarded text color, in
both themes. It exits non-zero with a table of failures.

## Design System Primitives ("Press Box")

Full change record for the v3.1 rebuild: the Build Log (`changes.html`, entry `v3.1-redesign`). The original markdown changelog is preserved in the portfolio `archive/` folder.

Reusable building blocks live in two places; all pages are migrated onto them:

- **Tokens** — `css/styles.css` `:root` (dark) + `[data-theme="light"]`:
  surfaces, ink (`--text`, `--text-muted`), edges (`--border`,
  `--border-strong`), the editorial voice (`--voice`, aliased by `--accent`),
  data colors (`--positive`, `--negative`, `--stars`, `--projected`, `--info`),
  motion (`--t-fast/base/slow`) and the type scale (`--fs-label` … `--fs-3xl`).
  No hex values outside these blocks and the two domain palettes in `config.js`.
- **Accent policy** — `--voice` is the editorial gold (eyebrows, mastheads,
  active nav). Team/player surfaces re-point `--accent` to ink via a single
  inheritance block on `.teams-layout, .modal, .entity-scope`, so team colors
  and data colors carry the personality there. Never fork a component for this.
- **CSS primitives** — end of `css/components.css`: `.ovr-badge` (canonical rating pill),
  `.delta-chip`, `.badge-proj` + `.is-projected` hatch, `.context-strip`, `.compare-pair`,
  `.tabs`/`.tab`, `.data-table`, `.skeleton*`, `.empty-state`/`.error-state`,
  `.eyebrow`/`.section-rule`, `.story-card`, `.chart-claim`.
- **Render helpers** — `js/ui.js`: `ovrPill()`, `posBadge()`, `deltaChip()`, `projBadge()`,
  `contextStrip()`, `comparePair()`, `statBig()`, `storyCard()`, `sparkline()`,
  `skeletonRows()`, `emptyState()`, `errorState()`. Pages call these instead of
  hand-writing pill/chip markup.

House rules the primitives enforce:

1. **No naked numbers** — big numerals (`statBig`) require context; ratings render as
   tier-colored pills with a `title`.
2. **Movement has a number** — `deltaChip` always shows arrow + signed value.
3. **Provenance is visible** — projected/model values pass `projected: true` and pick up
   the hatch + `PROJ` badge; never mixed silently with earned ratings.
4. **Escape by default** — all data strings route through `_esc()`.
5. **Loading is skeletons** (shaped like content), **empty states say why**, **errors are
   inline and honest**. Spinners never.

## Key Features

### Player Modal

Clicking any player card opens a full-screen modal with:

- OVR hero badge with tier color (Elite / Gold / Silver / Bronze / Developing)
- Season-by-season stat history
- SHAP feature breakdown — which stats drove the rating and by how much
- Similar players — top 5 comps from any era (cosine similarity across EDGE feature vectors)
- Trajectory indicator (year-over-year OVR change)

### Ratings Scatter Plot

Rating vs. Recruiting Stars with:

- Linear regression line across all filtered players
- Players 8+ OVR points above the line highlighted green ("overperformers" — the platform's core value proposition)
- Position group and team filters
- Hover tooltips; click any dot to open the player modal

### Similar Players

Precomputed cosine similarity across EDGE feature vectors (OVR ≥ 55 players only). Top 5 matches per player-season across all years — shows historical comps like "This WR plays like 2019 CeeDee Lamb."
